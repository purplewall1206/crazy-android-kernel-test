# CortenMM 移植最终报告

2026-09-23 19:5x。基线 android17-6.18，终态 HEAD 037bfbaed020，45 个项目提交、43 个 tag。
所有数字都指向 results/ 下的原始日志，没有一个是转述。

## 一、当初要证明什么，现在证明了没有

立项时（STATE 使命）定的是三件事：

**1. 干掉 VMA 后内核照常运行。** 成立。MODE 进程窗口域的内存现在完全不过 VMA 语义：匿名和
文件映射的建立、缺页、保护变更、fork、换入换出、回收、观察（maps/smaps/pagemap）、外部
访问（ptrace/process_vm/proc-mem）全部走 corten 元数据和事务。终判据是实测的，不是宣称的：
find_vma 五原语在窗口域的调用为零（J1，内核口径严格零），树上永远查不到窗口内不该有的 VMA
（J2，双走查器交叉核验一致），零改动回归集（JVM/metis/dedup/psearchy/lmbench）全过。
唯一的诚实化口径在 D20-a：委托遗留域（栈/vdso/brk/exec 映射）保留白名单 VMA，detached
carrier 作 rmap 锚——照论文原教旨全删是三倍工程量，这个取舍记在账上。

**2. 热路径有可测提升。** 成立，但要看哪条路（详见下节）。unmap 族是主要赢家。

**3. fork 等全地址空间操作允许论文量级回退。** 实际上没付这个代价：修完 A5（惰性 registry）
后 fork 比基线还快 10.65%。中途确实付过（最差 +516%），根因定位、修掉、数字留下。

## 二、性能账（全部同 boot 双臂对照，8 vCPU QEMU）

赢的：
- unmap-virt（PTE-less 窗口解除映射）：低竞争 t4 +1142%、t8 +2583%（五轮固化 + 终验复算）
- unmap（预映射区）：+45% ~ +142%
- mmap 全族：+141% ~ +251%（T1c 池生命周期税从 17.4µs 降到 1.3µs 之后）
- MODE munmap 单次：8554µs → 227.8µs（D15 born-atomic 修复）
- dedup（tcmalloc 档）：六个独立 boot 全正向，+8.7% ~ +19.2%
- swap/回收闭环：换出换入 69164 = 69164 笔笔对账；shrinker 自然换出 RSS 281MB → 3.8MB

平的：
- fork/fork+exec/shell：-10.65% / +3.77% / +0.52%（门限 ≤30%）
- jvm spawn：-4.57%（噪声族，收在 5% 线内）

输的（如实）：
- mmap-pf（映射区缺页）：-17% ~ -22%，五轮一致不是方差。归因到事务语义本身的固定成本
  （fill_upper + 锁区间 + 查询 + 标记），进了噪声地板。这是论文 per-fault 事务语义的价格。

没达标的：
- G3 的字面门（某单项稳定 ≥10%）没过——apps 全正但无单项稳定过线，按机制面定案。这条
  按原文登记 NOT MET，不粉饰。

头条证据：367K 个 perf 样本里 find_vma 和 mmap_lock 合计零命中。这是整个移植的核心主张，
M3 时证明，M-V 之后依然成立（J1 计数器长期在线监督）。

## 三、代码量账（如实：现在是净增，不是减少）

直接给数字：

- corten 侧（生产代码，不含测试）：19,676 行
- corten 侧（含 KUnit 测试，157 个用例）：36,256 行
- 被替代的 VMA 层三件（mmap.c + vma.c + maple_tree.c + mmap_lock.c）：13,360 行
- M-V 系列实际从 VMA 层核心文件删掉的部分：67 行

所以按今天的树算，**净增约 6,300 行生产代码**（19,676 − 13,360），如果只看"功能上已可
被 arena 取代"的那部分 VMA 代码。测试另计 16,600 行。

这个结果在 D12 就预告过："减代码是终态属性，不是中间步骤"。今天达成的是那个终态属性的前半
句——窗口域对 VMA 层的热路径依赖归零（J1 严格零 + J2 不变量活体成立），也就是说那 13,360
行对 MODE 进程而言已经是死代码，哪天 arena 变默认配置，它们整体可删。但"单内核双 MM"的
现实形态下它们还要服务非 MODE 进程，所以现在删不了。论文原型的"代码更少"主张，在这个移植
口径下不成立，成立的是"可删性已建立并有测量账本"。

## 四、正确性账

- syzkaller 两轮共 453 万次执行（corten=on 面 311 万），零内存安全崩溃，崩溃目录里 6 条
  全是环境噪音，逐条定性在档
- lockdep 家族全绿；DEBUG_ATOMIC_SLEEP 首开抓到 47 处原子内睡眠，修到零
- KCSAN 短跑零数据竞争（仅有的 2 条 WARN 与 A.1 基线对照确认为递减的长期项）
- 157 个 KUnit 锚；复审和独立验收层（J2 审计、J3 oracle、fork 差分锚）合计抓出并修复
  25+ 个真缺陷——包括混合态 fork 静默丢内容、rss 记账族错位、双源游标首行丢失、共享 PUD
  页搁浅这类只有真实负载形状才能暴露的问题
- 诚实登记的开放项：S-3 复测发现 read-back 期间换入计数平坦（窗口换入语义，升级臂留档）、
  bpftrace 口径缺 guest BTF、J3 跨内核字节对拍快照待补拍

## 五、结论

论文的核心论断——VMA 层不是热路径必需——在这个移植里成立并且是可以复核的：一个 MODE 进程
的全部窗口内存生命周期不再经过 VMA，内核照常运行，零改动应用全兼容，unmap/mmap 族拿到
数量级的提升，代价（mmap-pf 固定成本、约 6,300 行净增、委托域白名单）全部有测量和登记。
